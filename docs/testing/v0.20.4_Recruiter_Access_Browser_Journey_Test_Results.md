## Notes

- **Environment**: verified against the already-running local Docker stack (`applicant`, `admin`,
  `postgres`, `keycloak`, `keycloak-postgres`, `minio` containers up for 39+ minutes prior to this
  run) plus the host-run Ops Console (`npm run ops:start`, not running at the start of this
  verification pass — started for the `regression:all` gate command, since its `ops` area scenarios
  need it). No Docker image rebuild was needed: this iteration touches only host-run test
  fixtures/spec files and configuration (`tests/journeys/`, `playwright.config.ts`, `package.json`),
  not application source under `apps/applicant` or `apps/admin`.
- **Two real fixture bugs found and fixed by running against the live stack**, not assumed from
  reading code:
  1. First run failed at graduate-profile seeding: `assignWeekMissionToAcceptedApplicant` requires
     an `ACCEPTED` `Application` row for the tenant+program (`packages/db/src/mission-assignments.ts:187-192`)
     — a `TenantMembership` alone is not enough. `fixtures/graduate.ts` was missing the
     `createSubmittedApplication`/`applyStatusTransition` step `scripts/regression/run.ts`'s
     `createApplicationFixture` has; added.
  2. Second run failed at submission: `submitSubmission`'s readiness gate requires 4 journal
     entries per assignment attempt server-side (`getMissionSubmissionReadiness`), enforced
     independently of the applicant portal's own date-picker UI. `fixtures/graduate.ts` was missing
     the equivalent of `scripts/regression/run.ts`'s `ensureMinimumAssignmentJournals`; added
     (16 entries total, 4 per mission, sequential dates in January 2025 to avoid the
     one-entry-per-applicant-per-date constraint).
  3. Third run failed at the admin-approve and admin-reject steps: the shared `settledClick` helper
     (adapted from `applicant-arc.spec.ts`) waited only for a `POST` response, but
     `RecruiterRequestActions` sends `PATCH` (`apps/admin/app/api/recruiter-requests/[id]/route.ts`).
     Fixed by waiting for either method.
  4. Fourth run: both tests passed clean. See `D-104` for the full write-up.
- **DB cleanup verified directly**, not just inferred from the harness not throwing: after both
  journey runs, `graduate_profiles` and `recruiter_accounts` in the local database contained only
  pre-existing rows unrelated to this session's test runs (the seeded demo applicant's profile, and
  a manually-created recruiter account under the developer's own email) — zero
  `recruiter_access_requests`, zero `regression_data_markers`, and no `journey-graduate-program-*`
  `programs` rows left behind. `RecruiterAccount` rows created by the journey (one per submitted
  access request, keyed by `recruiterEmail`) are marked via `markRegressionData` inline in the
  spec, since it — like every other recruiter-flow entity — has no relation back to `User`/`Tenant`
  for the existing cleanup chain to reach (`v0.20.3`, D-103).
- **The recruiter's access token is never observed from a real API response** — by design, only
  `hashToken(rawToken)` is ever persisted, and no mailbox-capture harness exists in this repo. Each
  test's `system`-labeled steps inject a known raw token directly via Prisma immediately after the
  real state transition (PENDING creation via the real modal submission; APPROVED via the real
  "Approve & Send Email" click) so the recruiter's browser can drive `/graduates/verify` itself. See
  `D-104` and the plan's Security and Data Rules section for why this is not a weaker guarantee than
  it looks.
- Known gaps this iteration does not close (see `Regression_Scenarios.md` Known Gaps, unchanged from
  `v0.20.3`): the graduate-portal/recruiter feature (PR #62) remains undocumented in
  `Data_Model.md`/`Data_Dictionary.md`/`Architecture.md` beyond journey/regression pointers, and
  Journeys 2 (admin authoring) and 3 (org onboarding) from the original design doc remain deferred.
