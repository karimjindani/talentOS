## Notes

- **Migration verified against the real local dataset before applying**: a dry-run check
  confirmed 0 of 58 `GraduateProfile` rows and 0 of 31 `RecruiterAccessRequest` rows would be left
  without a resolvable tenant (every graduate has ≥1 `Application`; every access request has a
  non-nullable `graduateId`). `prisma migrate deploy` applied cleanly; `prisma migrate status`
  confirmed the schema up to date afterward.
- Docker containers (`applicant`, `admin`) were rebuilt against this branch and the DB confirmed
  on all 29 migrations before running the full regression suite, so `regression:all` exercised the
  actual built images, not just source. `/graduates` (public) returned HTTP 200 and
  `/recruiter-requests` (admin, unauthenticated) returned the expected 307 auth redirect.
- The `ops` console (`apps/ops`, host-run via `npm run ops:start`) was running for this
  `regression:all` run so the `ops` area (2 scenarios) could pass.
- **Known Gap carried forward, not introduced by this iteration**: `toggleSavedCandidate`
  (`packages/db/src/graduates.ts`) never calls `recruiterHasActiveAccess` — any recruiter session
  can save/unsave a public candidate without an approved grant for that tenant. Unrelated to tenant
  isolation (it was equally true before this iteration, platform-wide); recorded in
  `docs/Regression_Scenarios.md` Known Gaps.
- **Known Gap, new**: the acute cross-tenant bug fix in
  `apps/applicant/app/api/graduates/request-access/route.ts` (picking any tenant's first public
  graduate) is verified by code review and the DB-layer tenant-isolation regression scenario
  above, not by a dedicated HTTP-level regression test — this route's suite has no existing
  HTTP-level coverage to extend (consistent with the rest of the public graduate routes, which are
  exercised only at the `packages/db` layer per `docs/Testing_Strategy.md`).
