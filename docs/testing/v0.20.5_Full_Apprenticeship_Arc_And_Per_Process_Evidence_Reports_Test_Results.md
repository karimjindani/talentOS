## Notes

- **Environment**: verified against the already-running local Docker stack, plus the host-run Ops
  Console (already up from `v0.20.4`'s own verification pass). No image rebuild needed — this
  iteration touches only host-run test/report code, not application source.
- **Six real issues found and fixed by running against the live stack**, none of them application
  bugs:
  1. `assignWeekMissionToAcceptedApplicant` requires an `ACCEPTED` `Application` row — carried
     over correctly from `v0.20.4`'s `fixtures/graduate.ts`, but this iteration's own
     `applicant-arc.spec.ts` rewrite didn't need a new instance of this (the arc already applies
     through the real UI); listed for completeness of what was re-verified, not a new find.
  2. The submission review page's accept control reads **"Accept submission"**, not "Accepted"
     (that literal text belongs to the *application*-review page's button, a different
     page/component) — and requires a 1-5 rating filled in first, or `reviewSubmission` throws.
     The original single-week arc never exercised acceptance at all (it stopped at
     `NEEDS_REVISION`), so there was no working precedent step to copy; fixed by filling
     `input[name="rating"]` before the click.
  3. `DashboardConsentGate`'s `onPublish` immediately `router.push()`es to `/dashboard/consent` —
     the click's own transient "Consent recorded" success text is replaced by that navigation
     before it's ever observable. Fixed by asserting on `/dashboard/consent`'s own durable status
     banner instead.
  4. The public `/graduates` directory defaults to 6-per-page sorted by highest rating, across
     every tenant's published graduates (by design — a public, cross-tenant listing). With enough
     other fixtures' graduates already in the local database, this run's own applicant sorted past
     page 1 and the bare visibility assertion failed. Fixed by searching the directory by name
     first, in both `applicant-arc.spec.ts` and (the same latent issue, now exposed) two spots in
     `recruiter-access.spec.ts`.
  5. `/api/graduates/request-access` attaches every submission to "the first public graduate
     profile" in the whole database, not the requesting test's own one. `recruiter-access.spec.ts`
     asserted the verify redirect landed on its own graduate's slug specifically — true only by
     coincidence in an otherwise-empty database. Fixed by asserting the redirect reaches *some*
     portfolio (proving verify itself worked), then separately navigating to the run's own
     graduate's portfolio directly (proving the grant covers every published graduate, which is
     the actual behavior being tested).
  6. The applicant's Prisma `User` row was never marked for regression cleanup at all (self-signup
     provisions the Keycloak identity; the Prisma row is created lazily by the app on the
     applicant's first tenant-scoped write — submitting the application, not signing in). Harmless
     before this iteration, since no journey ever published a profile from it; a real leak now — 28
     orphaned applicant `User` rows, several already carrying a published `GraduateProfile`, had
     accumulated in the local database purely from this session's own debugging runs before the fix
     landed. Same root cause exposed a second, related gap: `RecruiterAccessRequest` was not a
     tracked cleanup entity type either, for the reason in finding 5 above (its graduate isn't
     reliably the requesting run's own) — both are fixed; see `packages/db/src/regression.ts` and
     `Decision_Log.md` `D-105`.
- **DB cleanup verified directly** before and after the final clean run: `select count(*) from
  users where email like 'journey-%'`, the equivalent join through `graduate_profiles`,
  `recruiter_accounts`, and `recruiter_access_requests` (all filtered to this harness's
  `journeys.talentos.local` email domain) each returned `0` after the run that produced the
  evidence used for the PDFs below — not inferred from the harness not throwing.
- **PDF report visually inspected** (`04-final-mission-public-profile.pdf`): eyebrow header, stat
  tiles, note callout, and per-step cards all render correctly with embedded screenshots; matches
  the reference report's structural language (branded eyebrow/title, stat tiles, numbered badges,
  colored pills, boxed cards) using talentOS's own brand blue/navy. One pre-existing app behavior
  is now visible in that PDF's evidence and worth a reader's awareness: the published profile shows
  a placeholder "0.0" rating rather than the applicant's real ~4.4 average — see the plan's
  Security and Data Rules "Observed, not fixed" note.
- Known gaps this iteration does not close (see `Regression_Scenarios.md` Known Gaps): the
  graduate-portal/recruiter feature (PR #62) remains undocumented in
  `Data_Model.md`/`Data_Dictionary.md`/`Architecture.md` beyond journey/regression pointers;
  Journeys 2 (admin authoring) and 3 (org onboarding) from the original design doc remain
  deferred; and the `overallRating: 0` placeholder behavior noted above is recorded, not fixed.
