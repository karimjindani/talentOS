# v0.20.11 Deadline Timezone Fix, Graduate Portal Tenant Isolation, and Recruiter Portfolio Data

Code version: `v0.20.11`

Previous baseline: `v0.20.10`

Plan status: Implemented

## Summary

Three related fixes shipped together on one branch, per explicit direction: (1) mission deadlines
landed on Thursday 23:59:59.999 **UTC**, which is already Friday morning in Pakistan Standard Time
— shifted to land before Friday in the tenant's own local time; (2) the public graduate portal and
recruiter access grants had no tenant scoping at all, pooling every tenant's published graduates
into one shared directory and letting an approved recruiter (or a tenant admin) reach another
tenant's data — closed with a schema change plus tenant-scoping through every public and
recruiter-facing read/write path; (3) the recruiter-facing portfolio dropped two real (not
placeholder) fields — `Mission.competencyTags` and `SubmissionReview` revision history — now
surfaced.

## Scope

- `computeMissionDeadline` (`packages/db/src/mission-assignments.ts`) now stores the Thursday
  cutoff as `18:59:59.999 UTC` (== `23:59:59.999` Pakistan Standard Time, UTC+5).
- New `GraduateProfile.tenantId` and `RecruiterAccessRequest.tenantId` columns (migration
  `20260824090000_v0_20_11_graduate_portal_tenant_isolation`), backfilled from each graduate's most
  recent `Application.tenantId` (not `Program.tenantId`, which is null on 43% of existing rows).
- Every public/recruiter `packages/db/src/graduates.ts` function now takes and enforces a
  `tenantId`: `getPublicProfiles`, `getPublicProfile`, `getAllAccessibleGraduates`,
  `getFullProfileForRecruiter`, `getRecruiterGraduateContact`, `getGraduatePhoto`,
  `toggleSavedCandidate`, `getRecruiterDashboard`, and the admin review functions
  (`getPendingAccessRequests`, `getAccessRequestDetail`, `approveAccessRequest`,
  `rejectAccessRequest`, `revokeAccessRequest`, `getAccessRequestStats`). `recruiterHasActiveAccess`
  (private) now grants access per tenant, not platform-wide.
- Every route under `apps/applicant/app/api/graduates/**` and the admin
  `apps/admin/app/api/recruiter-requests/**`/`apps/admin/app/recruiter-requests/**` pages resolve
  and thread the current tenant through, using the same `getTenantContext()` +
  `getTenantBySlug()` pattern already established elsewhere in this app.
- Fixed the acute case: `apps/applicant/app/api/graduates/request-access/route.ts` previously
  picked *any* tenant's first public graduate (`findFirst({ where: { publicProfileEnabled: true }
  })`, no tenant filter) to attach a request to; now scoped to the resolved tenant.
- `getFullProfileForRecruiter` now selects `Mission.competencyTags` and each assignment's
  `SubmissionReview` history (round/decision/feedback) plus `revisionCount`/`reviewOutcome`;
  rendered on `apps/applicant/app/graduates/[slug]/portfolio/page.tsx` as competency-tag chips and
  an expandable review-history panel.

## Out of Scope

- Per-tenant configurable timezone for the deadline cadence — this hardcodes Pakistan Standard
  Time for the one timezone this deployment actually needs; a real per-tenant timezone field is
  deferred future work (unchanged from the existing D-093 decision).
- `RecruiterAccount`/`RecruiterSession`/`SavedCandidate` gained no new column — recruiter identity
  stays cross-tenant by email, and a saved candidate's tenant is resolved via the graduate relation
  rather than a denormalized column.
- The pre-existing gap where `toggleSavedCandidate` never checks `recruiterHasActiveAccess` at all
  (any recruiter session can save/unsave a public candidate without an approved grant) is unrelated
  to tenant isolation and left unfixed — noted as a Known Gap.

## Test Scenarios

- **Scenario**: A mission deadline lands before Friday starts in the tenant's local time.
  **Actor**: Accepted applicant.
  **Preconditions**: A `NOT_STARTED` mission assignment.
  **Steps**: Applicant accepts the assignment.
  **Expected result**: `deadlineAt` is `18:59:59.999 UTC` (23:59:59.999 PKT) on the computed
  Thursday, not `23:59:59.999 UTC` (which would already be Friday morning PKT).
  **Automation**: Added this iteration (`regression:missions` — "Accepting a mission sets a
  Thursday deadline with at least four working days (v0.20.0)", hour assertion strengthened; plus
  `mission-assignments.test.ts`).

- **Scenario**: The public graduate directory is tenant-isolated.
  **Actor**: Anonymous visitor browsing under a specific tenant's host.
  **Preconditions**: Two tenants each with a published, consented graduate profile.
  **Steps**: Request the directory and a direct slug lookup scoped to tenant A.
  **Expected result**: Tenant B's graduate never appears in tenant A's directory listing, and a
  direct slug lookup for tenant B's graduate under tenant A returns not-found rather than filtering
  it out client-side.
  **Automation**: Added this iteration (`regression:public-portal` — "The graduate directory and
  recruiter access grants are tenant-isolated (v0.20.11, D-110)").

- **Scenario**: An approved recruiter access grant does not cross tenants.
  **Actor**: A recruiter with an `APPROVED` access request under tenant A.
  **Preconditions**: A second tenant B with its own published graduate.
  **Steps**: The recruiter attempts to view tenant B's graduate's full portfolio, and the
  accessible-graduates list, scoped to tenant B.
  **Expected result**: Both are denied — the recruiter's grant only ever resolves for the tenant it
  was approved under.
  **Automation**: Added this iteration (same `regression:public-portal` scenario, second half).

- **Scenario**: A tenant admin cannot approve, reject, or revoke another tenant's recruiter
  access request.
  **Actor**: ORG_ADMIN of tenant A.
  **Preconditions**: A `PENDING`/`APPROVED` `RecruiterAccessRequest` belonging to tenant B.
  **Steps**: Admin calls approve/reject/revoke with tenant A's resolved tenant id against tenant
  B's request id.
  **Expected result**: Each call throws "not found" rather than acting on the other tenant's
  request.
  **Automation**: Added this iteration (`packages/db/src/graduates.test.ts` — "throws for a missing
  request (including one that belongs to another tenant)" for `approveAccessRequest` and
  `revokeAccessRequest`; "throws for a request that belongs to another tenant" for
  `rejectAccessRequest`).

- **Scenario**: The recruiter portfolio surfaces competency tags and revision-round history.
  **Actor**: A verified recruiter with an active grant.
  **Preconditions**: A graduate with at least one assignment that required a revision round before
  acceptance.
  **Steps**: Recruiter opens the graduate's full portfolio.
  **Expected result**: Each assignment shows its mission's competency tags and, when
  `revisionCount > 0`, how many feedback rounds it took plus the full round-by-round history —
  not just the latest decision.
  **Automation**: Added this iteration (`packages/db/src/graduates.test.ts` — "getFullProfileForRecruiter
  surfaces competency tags and revision history for each assignment").

## Security and Data Rules

- Tenant isolation is enforced at the query layer (every `where` includes `tenantId`), not just at
  the UI — a direct API call with a valid recruiter session but the wrong tenant context is denied
  the same way a browser request would be.
- `RecruiterAccessRequest.tenantId` is always derived server-side from the target graduate's own
  `tenantId` at creation time (`createRecruiterAccessRequest`), never trusted from request input,
  so a grant can't be mis-attributed to the wrong tenant even if a caller passed one.
- No new PII exposure: competency tags and revision history are drawn from data already visible to
  the graduate's own reviewer during the original review; nothing new is exposed to recruiters that
  the tenant's own staff didn't already record.
