# v0.20.2 Decision Log Integrity And Opt-In Request Logging

Code version: `v0.20.2`

Previous baseline: `v0.20.1`

Plan status: Implemented

## Summary

Four defects surfaced when `v0.20.0` (PR #56), the E2E-evidence CI job (PR #57), `v0.20.1` (PR #59) and
a `vision.md` revision (PR #58) all merged into `main` within about a day. Three are documentation
integrity problems caused by branches that could not see each other's allocations; the fourth is a
production concern in the request logging `v0.20.1` introduced. None was caught by CI, because CI gates
on code, not on whether the documentation the SSDLC requires actually exists and agrees with itself.

## Scope

1. **Duplicate decision identifier.** `v0.19.7` and `v0.20.0` each allocated `D-096` on separate
   branches; both merged, so a citation of `D-096` resolved to two different decisions. The `v0.19.7`
   entry is renumbered to `D-101` and relocated after `D-100` so the log stays in numeric order, and
   its six inbound references are repointed. `v0.20.0`'s `D-096`–`D-100` keep their numbers because
   `Deployment.md` and `Product_Backlog.md` cite them as a contiguous range.
2. **`v0.20.1` shipped with no plan or test-results pair.** Both are reconstructed from the merged
   commits and the CI evidence that iteration produced, and marked as retroactive. The traceability
   chain is completed with a `v0.20.1` section in `Regression_Scenarios.md`.
3. **`CI_CD_Pipeline.md` had its version header bumped to `v0.20.1` with no content change.** It still
   described a two-job pipeline and stated that scenario regression "is a local/Ops-Console capability,
   not a CI stage" — untrue since PR #57. The `e2e-evidence` job is now documented.
4. **Request logging was unconditional.** Moved behind `logRequest` in
   `packages/auth-web/src/request-log.ts`, gated on `REQUEST_LOG === "1"` and filtered so `_next` and
   static-asset paths do not drown out real navigations.

Stale counts corrected along the way: `Regression_Scenarios.md` claimed 40 and 42 scenario objects in
two places; the runner has **53**, confirmed against both a structural parse of `run.ts` and the
per-area totals in `v0.20.1`'s CI artifact.

## Out of Scope

- **Renumbering `v0.20.0`'s `D-096`–`D-100`** — the alternative resolution of the collision. Rejected:
  five identifiers and their range citations would move instead of one.
- **Retrofitting plan/test-results pairs for older iterations.** Only `v0.20.1` is filled in, because
  it is the gap this review found.
- **Structured/JSON logging and log shipping.** Still no aggregation target; stdout is enough.
- **A CI check that decision identifiers are unique and every version has its doc pair.** The right
  long-term fix for classes 1–3, but it is its own iteration. Recorded in `Product_Backlog.md`.
- **`docs/vision.md` numbering from PR #58.** Another contributor's in-flight editorial pass.

## Test Scenarios

The middleware is the auth boundary for both portals, so the scenarios that matter most are the
existing authorization and tenant-isolation ones — this change must be invisible to them.

- **Scenario**: Request logging is silent unless explicitly enabled.
  - **Actor**: Any visitor, in an environment that does not set `REQUEST_LOG`.
  - **Preconditions**: `REQUEST_LOG` unset, or set to anything other than `"1"`.
  - **Steps**: Issue requests to either portal.
  - **Expected result**: No request log lines. A deployed environment is quiet by default; `"0"`,
    `"true"`, `"yes"` and `""` are all off, so a half-configured value cannot silently enable it.
  - **Automation**: `Added this iteration` — `packages/auth-web/src/request-log.test.ts`.

- **Scenario**: Request logging is enabled for the local Docker stack.
  - **Actor**: Developer running `npm run local:bootstrap`.
  - **Preconditions**: `docker-compose.yml` defaults `REQUEST_LOG` to `1` for both apps.
  - **Steps**: Load a page on each portal, then run `docker compose logs applicant admin`.
  - **Expected result**: One line per request — `[app] <iso> <method> <path> tenant=<slug> auth=<bool>`.
    The observability `v0.20.1` added is preserved. Notably this must hold even though the stack runs
    `NODE_ENV: production`, which is why the flag is explicit rather than environment-inferred.
  - **Automation**: `Deferred` — no log-capture helper in the runner; the enable rule and format are
    unit-tested. Recorded as a Known Gap in `docs/Regression_Scenarios.md`.

- **Scenario**: Asset and Next-internal requests do not produce log lines.
  - **Actor**: Any visitor loading a page that pulls files from `public/`.
  - **Preconditions**: Logging enabled.
  - **Steps**: Load a page; inspect the log.
  - **Expected result**: `/dashboard` is logged; `/logo.svg`, `/styles.css`, `/_next/data/...` and
    `/_next/webpack-hmr` are not. A path segment that merely contains a dot
    (`/missions/v1.2-release`) is still logged — the filter matches extensions, not any dot.
  - **Automation**: `Added this iteration` — `packages/auth-web/src/request-log.test.ts`.

- **Scenario**: An applicant session still cannot reach the admin portal.
  - **Actor**: An authenticated applicant.
  - **Preconditions**: Valid applicant session; admin middleware now calls `logRequest` before its
    authorization branch.
  - **Steps**: Present the applicant session to the admin portal.
  - **Expected result**: Denied exactly as before — redirected to `/forbidden`. Inserting the log call
    must not alter the authorization path. This is the role-denial case.
  - **Automation**: `Added this iteration` (coverage retained) — `regression:auth`, the existing
    "Applicant session cookie does not grant admin portal access (v0.20.1)" scenario.

- **Scenario**: Tenant resolution and the tenant response header are unchanged.
  - **Actor**: Users of two different tenants.
  - **Preconditions**: Two tenant subdomains resolving to the stack.
  - **Steps**: Request each portal on each subdomain.
  - **Expected result**: `x-talentos-tenant` still carries the resolved slug and cross-tenant reads are
    still denied. This is the tenant-isolation case.
  - **Automation**: `Added this iteration` (coverage retained) — `regression:tenant`.

- **Scenario**: A failing console cannot break a request.
  - **Actor**: Any visitor, in a container whose stdout has been closed.
  - **Preconditions**: Logging enabled; `console.log` throws (e.g. `EPIPE` during teardown).
  - **Steps**: Issue a request.
  - **Expected result**: The request is served normally; the logging failure is swallowed. An
    observability concern must not be able to break the auth middleware hosting it. This is the
    negative/edge case.
  - **Automation**: `Added this iteration` — `packages/auth-web/src/request-log.test.ts`.

- **Scenario**: Every decision identifier in the log is unique.
  - **Actor**: Anyone citing a `D-0NN` from a commit trailer or doc.
  - **Preconditions**: `docs/Decision_Log.md` as merged.
  - **Steps**: `grep -oE "^## D-[0-9]+" docs/Decision_Log.md | sort | uniq -d`
  - **Expected result**: No output. Every citation resolves to exactly one decision.
  - **Automation**: `Deferred` — a documentation-integrity check, not a runtime scenario. A CI guard is
    recorded in `Product_Backlog.md`; run manually until then.

## Security and Data Rules

- No schema, migration or data-shape change. `Data_Model.md` and `Data_Dictionary.md` are unchanged
  for this iteration, noted explicitly rather than skipped.
- `logRequest` runs **before** the authorization branch in both middlewares and never short-circuits,
  returns, or throws, so it cannot affect an access decision.
- The log records path, tenant slug and a boolean auth flag only — no user identifiers, session tokens,
  query strings or bodies. Defaulting to off means a deployed environment emits nothing unless someone
  deliberately turns it on.
- `REQUEST_LOG` is not a secret and carries no credential.
