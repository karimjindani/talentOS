# v0.20.4 Recruiter Access Browser Journey

Code version: `v0.20.4`

Previous baseline: `v0.20.3`

Plan status: Implemented

## Summary

Adds a fourth Playwright journey, `recruiter-access.spec.ts`, that drives the recruiter
access-request lifecycle through real browser sessions across both the public applicant portal
(`/graduates`, `/graduates/[slug]`, `/graduates/verify`, `/recruiter`) and the admin portal
(`/recruiter-requests`). `v0.20.3` proved this lifecycle correct at the regression/integration
level (`packages/db/src/graduates.test.ts`, `regression:public-portal` scenarios 6-7) but never
through an actual browser — this iteration closes that gap the same way `applicant-arc.spec.ts`
closed it for the applicant/reviewer flow, and gives the recruiter flow its own entry in the
journey design doc's journey list.

## Scope

- **New `recruiter` actor** (`tests/journeys/fixtures/types.ts` — `Actor` union) and its portal
  routing (`tests/journeys/fixtures/actors.ts` — `portalUrl()`): recruiters browse the public
  graduate directory and `/recruiter` dashboard, both served from the applicant app
  (`APPLICANT_PORT`), not the admin app — unlike every existing non-applicant actor, which
  defaults to `ADMIN_PORT`. `portalUrl()`'s actor-to-port mapping needs a third case, not just a
  new entry in the existing applicant/everything-else split.
- **`tests/journeys/recruiter-access.spec.ts`** — two test blocks:
  1. The full lifecycle: browse the directory → open the `PublicPortalNav`'s "Access Full
     Profiles" modal (`RecruiterAccessModal.tsx`, posting to `/api/graduates/request-access` — a
     single global request, not a per-graduate one; the older slug-specific `RecruiterAccessForm`
     component exists in the tree but is unused by any page, confirmed by grep, and is out of
     scope here) → confirm the still-PENDING request is refused at `/graduates/verify` → admin
     approves via a real browser session on `/recruiter-requests/[id]` → recruiter verifies and
     lands on the full portfolio (the verify page's own client-side redirect, not a followed link)
     → recruiter saves the candidate and confirms it appears on `/recruiter`'s dashboard → admin
     revokes access → the same token is refused again.
  2. Pending/rejected refusal and the rejection-reason surfacing, verified through
     `/graduates/verify`'s actual rendered error states (`Access Pending Review`,
     `Request Rejected`, with the admin's stated reason shown on-page) rather than only asserting
     the API response shape, which is all the existing regression scenario does.
- **`tests/journeys/fixtures/graduate.ts`** (new) — seeds the one published, consented graduate
  every step in this journey needs, built directly against `@talentos/db` business-logic
  functions in a dedicated program (four missions, four accepted+rated submissions,
  `createOrUpdateGraduateProfile`) rather than by driving the applicant portal through a real
  browser — that end-to-end proof is `applicant-arc.spec.ts`'s job. Mirrors
  `scripts/regression/run.ts`'s `createGraduateEligibleFixture`.
- **Raw-token handoff inside the fixture, not a mailbox.** No email-capture harness
  (e.g. MailHog) exists in this repo. `approveAccessRequest` already returns the raw token
  alongside the row it persists as a hash (`packages/db/src/graduates.ts:216`) — the same value
  the real email route embeds in the verification link. The journey fixture captures that return
  value directly (a server-side call, mirroring how tenant/admin-identity setup already bypasses
  the UI elsewhere in this harness) and uses it to build the URL the recruiter's browser
  navigates to. Documented explicitly in Security and Data Rules below so this shortcut doesn't
  get mistaken for proving the email itself was sent correctly.
- **CI wiring**: added to the existing `e2e-evidence` job's journey run alongside `applicant-arc`
  and `docs-only` — no new CI job, same evidence pipeline (JSON, screenshots, Markdown step
  summary, combined PDF) built in `v0.20.3`.
- **`docs/designs/2026-08-13-journey-e2e-evidence-design.md`**: "Scope — three journeys" becomes
  four, adding a "Recruiter access arc" entry in the same one-paragraph style as the existing
  three, so the design doc stays the accurate record of what the journey suite actually covers.

## Out of Scope

- **Proving the real email was sent/received.** This journey proves the verification-link
  *destination* behaves correctly once a recruiter has a valid link; it does not stand up a
  mailbox to prove the email route actually dispatched one. `packages/db/src/graduates.test.ts`
  already covers `sendRecruiterAccessEmail` being called with the right arguments at the unit
  level. Building real mailbox capture is a separate, larger infrastructure undertaking.
- **Multi-recruiter / multi-graduate directory-scale assertions** (e.g., a recruiter's directory
  view reflecting N published graduates at once). Already covered at the regression/integration
  level (`packages/db/src/graduates.test.ts`, scenario 6's "every published graduate" assertion);
  this journey proves one browser-driven pass through the lifecycle for one graduate, not
  directory-listing completeness.
- **Backfilling `Data_Model.md` / `Data_Dictionary.md` / `Architecture.md` / user-guide
  documentation for the graduate-portal/recruiter feature itself** (PR #62). Still an open,
  unassigned gap recorded in `v0.20.3`'s plan and `docs/Regression_Scenarios.md`; unchanged by
  this iteration, which only adds browser-level test coverage.
- **Journeys 2 (admin authoring) and 3 (org onboarding + team collaboration)** from the original
  design doc — still deferred, unrelated to this change.

## Test Scenarios

### 1. Recruiter completes the full access-request lifecycle through real browser sessions on both portals

- **Scenario**: Recruiter completes the full access-request lifecycle through real browser
  sessions on both portals
- **Actor**: recruiter (unauthenticated public visitor, not a tenant member); ORG_ADMIN reviewer
- **Preconditions**: a fresh journey-scoped tenant with one published, consented graduate profile
  (`fixtures/graduate.ts`'s `provisionPublishedGraduate`, seeded directly rather than re-driving
  the applicant's full consent flow, which `applicant-arc` already covers)
- **Steps**: recruiter opens `/graduates`, sees the graduate listed → opens the nav's "Access Full
  Profiles" modal and submits it (name, email, organization, designation, hiring requirement) →
  a harness step binds a known raw token to the still-PENDING request (see Security and Data
  Rules) and the recruiter's `/graduates/verify` attempt with it is refused → admin, in a real
  browser session (existing `completeLogin` flow), opens `/recruiter-requests/[id]` and clicks
  "Approve & Send Email" → a harness step binds a second known raw token to the now-APPROVED
  request → recruiter's browser opens `/graduates/verify?token=<raw>`, is redirected to
  `/graduates/[slug]/portfolio`, and the full portfolio renders → recruiter clicks "Save
  candidate" → `/recruiter` dashboard shows the graduate under "Saved candidates" → admin clicks
  "Revoke Access" on `/recruiter-requests/[id]` → recruiter's same token is refused again at
  `/graduates/verify`
- **Expected result**: every UI-visible state transition matches the DB-level lifecycle already
  proven in `v0.20.3`'s regression scenario 6 (create → PENDING refuses → approve → verify →
  directory/portfolio access → revoke → access removed everywhere); each step captures a
  full-page screenshot as evidence
- **Automation**: Added this iteration — `tests/journeys/recruiter-access.spec.ts`
  (`npm run journeys:recruiter`)

### 2. Pending and rejected recruiter access requests are refused in the browser, with the rejection reason shown on-page

- **Scenario**: Pending and rejected recruiter access requests are refused in the browser, with
  the rejection reason shown on-page
- **Actor**: recruiter; ORG_ADMIN reviewer
- **Preconditions**: two recruiters each submit the "Access Full Profiles" modal for the same
  published graduate, creating two independent PENDING requests; an admin then rejects one via a
  real browser session on `/recruiter-requests/[id]` with a stated rejection reason, leaving the
  other PENDING
- **Steps**: a harness step binds known raw tokens to both requests (see Security and Data
  Rules); recruiter's browser opens `/graduates/verify?token=<pending>`; recruiter's browser opens
  `/graduates/verify?token=<rejected>`
- **Expected result**: the PENDING case renders "Access Pending Review" and grants no session;
  the REJECTED case renders "Request Rejected" with the admin's stated reason shown verbatim in
  the page's reason panel, and grants no session
- **Automation**: Added this iteration — `tests/journeys/recruiter-access.spec.ts` (second test
  block in the same spec file), `npm run journeys:recruiter`

### Tenant isolation

Not applicable, for the same reason `v0.20.3`'s plan gave: graduate profiles are deliberately
public and cross-tenant-discoverable by design (a public directory, not a tenant-scoped
resource), and recruiters are not tenant members. This journey's tenant is provisioned only to
host the one graduate profile under test, using the harness's existing per-run isolation
(`jrn-<runId>.lvh.me`) — not because the recruiter flow itself has a tenant-isolation property to
prove.

## Security and Data Rules

- The raw access token is never recoverable from any API response or from the database (only
  `hashToken(rawToken)` is ever persisted) — not on creation, not on approval, and not on resend.
  The harness therefore injects its own known raw token directly via Prisma immediately after each
  real state transition (PENDING creation, APPROVED via the real "Approve & Send Email" click),
  so the recruiter's browser has a value it can actually use against `/graduates/verify`. This
  proves the verification endpoint and its UI, not email delivery — see Out of Scope.
- Recruiter access tokens must still never appear in the journey's own evidence artifacts in
  plaintext beyond what's needed to drive the browser — the fixture must not log or persist the
  raw token outside the single navigation call that consumes it.
- Revocation must be proven total in the browser, not just at the API layer: the same token must
  be refused after "Revoke Access," matching the "revocation is total... not partial" requirement
  `v0.20.3`'s plan already established for the underlying business logic.
