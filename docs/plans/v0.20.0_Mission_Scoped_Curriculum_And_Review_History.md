# v0.20.0 Mission-Scoped Curriculum, Review History And Markdown Mission Authoring

Code version: `v0.20.0`

Previous baseline: `v0.19.6`

Plan status: Implemented

## Summary

Seven related changes that make the curriculum belong to a mission rather than to a week, make the
review record complete enough to evaluate an applicant, and remove the two biggest authoring chores.
Tasks become mission-scoped; every review decision is kept instead of overwritten; the Journal tab is
grouped by mission and can no longer be dated before the mission started; the admin journal wall
collapses; three gaps that stranded enrolled applicants are closed; and a mission can be created by
uploading one Markdown file.

## Scope

- `ProgramTask.missionId` (required) — tasks authored per mission; readiness gates on the assignment's
  mission. Migration `20260808090000_program_task_mission_scope`.
- Repeat recovery covers `ACCEPTED` applications with a dangling `REPEAT`, not only parked ones.
- `SubmissionReview` append-only history + `MissionAssignment.reviewOutcome` / `revisionCount`,
  backfilled from `audit_logs`. Migration `20260810120000_submission_review_history`.
- `getApplicantEvaluationSummary` / `formatEvaluationSummaryForPrompt` for AI evaluation.
- Applicant Journal grouped into collapsible per-mission sections with View/Edit affordances.
- Journal entry dates bounded below by the assignment's `acceptedAt`.
- Admin submission review: review-history panel; journal rendered as disclosures.
- Enrolled-with-no-mission: reviewer notification on acceptance, backfill serves each applicant's
  actual next week, explicit applicant waiting states.
- Mission import from a Markdown spec, reusing the seed corpus parser
  (`packages/db/src/mission-spec.ts`).

## Out of Scope

- Retiring the fixed 3-step mission workflow (`mission-tasks.ts`) in favour of authored steps —
  discussed and deferred; it rewrites the mission workspace UI and needs its own iteration.
- Storing uploaded mission spec files (MinIO / `StoredFile`); specs are parsed and discarded.
- YAML frontmatter for mission metadata — rejected to keep one source of truth and keep seed specs
  importable unchanged.
- Re-importing Markdown over an existing mission from the edit page.
- Correcting the 8 pre-existing journal entries that pre-date their mission; they are locked and
  left as history.

## Test Scenarios

- **Scenario**: Tasks are authored per mission
  - **Actor**: ORG_ADMIN.
  - **Preconditions**: a program with at least two published missions in the same week.
  - **Steps**: open **Tasks**, pick the program, pick a mission, add a required task; open the other
    mission.
  - **Expected result**: no editor appears until a mission is chosen; the task is stored with that `missionId`
    and the mission's `weekNumber`; the sibling mission does not list it.
  - **Automation**: `Added this iteration` — `regression:missions` "Prerequisite weekly tasks are stored
    and surfaced to applicants (v0.20.0)" and `regression:admin` content scenario.

- **Scenario**: Submission readiness gates on the assignment's own mission tasks
  - **Actor**: accepted applicant.
  - **Preconditions**: required task on the assigned mission, another required task on a different
    mission in the same week.
  - **Steps**: complete only the other mission's task, attempt to submit.
  - **Expected result**: submission is blocked naming the assigned mission's task; the other mission's task is
    irrelevant.
  - **Automation**: `Added this iteration` — `regression:missions` "Submission readiness requires weekly
    tasks, four current-attempt journals, and all evidence URLs".

- **Scenario**: Repeat onto a different mission brings that mission's tasks
  - **Actor**: ORG_ADMIN then accepted applicant.
  - **Preconditions**: applicant with a submitted attempt; a second published mission for the same week
    carrying its own required task.
  - **Steps**: review as **Repeat week**; inspect attempt 2 readiness.
  - **Expected result**: attempt 2 requires the new mission's task (not yet complete) and resets journal
    progress; the completion on the earlier mission is preserved.
  - **Automation**: `Added this iteration` — `regression:missions` "Repeat-week attempts preserve journal
    history without duplicate or infinite loops".

- **Scenario**: Publishing a mission rescues a dangling repeat
  - **Actor**: ORG_ADMIN.
  - **Preconditions**: applicant whose latest attempt is `REPEAT` with no successor, application
    `ACCEPTED`.
  - **Steps**: publish a new mission for that week.
  - **Expected result**: an attempt at `latest.attemptNumber + 1`, `NOT_STARTED`, on a mission never served to
    them; applicant notified. A `DRAFT` mission must **not** trigger it.
  - **Automation**: `Deferred` — covered by unit tests and manual portal verification; recorded in
    `docs/Regression_Scenarios.md` Known Gaps.

- **Scenario**: Review history survives the revision loop
  - **Actor**: ORG_ADMIN.
  - **Preconditions**: a submission in `SUBMITTED`.
  - **Steps**: **Request changes** with feedback, applicant resubmits, **Accept** with different feedback.
  - **Expected result**: two `SubmissionReview` rows (round 1 `CHANGES_REQUESTED`, round 2 `ACCEPTED`), round 1
    feedback intact, assignment `reviewOutcome = ACCEPTED_AFTER_CHANGES`, `revisionCount = 1`.
  - **Automation**: `Added this iteration` — `regression:missions` "Submission loop: draft, submit,
    request changes, resubmit, accept — with notifications and audit".

- **Scenario**: Journal entries cannot pre-date the mission start
  - **Actor**: accepted applicant.
  - **Preconditions**: mission accepted today.
  - **Steps**: attempt an entry dated before acceptance, including with the picker's `min` removed.
  - **Expected result**: rejected naming the earliest valid date, nothing written; the start day itself and any
    later day up to today are accepted; an edit cannot move a saved date back past the start.
  - **Automation**: `Added this iteration` — `regression:applicant` "Applicant completes an assigned-week
    task and future journal dates are rejected" and `regression:journal` scenarios.

- **Scenario**: Journal is grouped by mission, with a repeated week kept separate
  - **Actor**: accepted applicant with a repeated week.
  - **Steps**: open **Journal**.
  - **Expected result**: one collapsible section per mission, newest first, only the first expanded; the repeated
    week appears twice with **Attempt N** labels; locked entries show **Locked** instead of Edit.
  - **Automation**: `Deferred` — UI-only; verified in the portal and by `view-model.test.ts`. Recorded in
    `docs/Regression_Scenarios.md` Known Gaps.

- **Scenario**: An applicant enrolled with no mission is not stranded silently
  - **Actor**: ORG_ADMIN then applicant.
  - **Preconditions**: a program with no published mission.
  - **Steps**: accept an application; later publish a Week 1 mission; pass it; publish Week 2.
  - **Expected result**: acceptance succeeds, no assignment, **reviewers notified**; the applicant sees an
    explicit "no missions yet" state; publishing Week 1 assigns them; after passing, publishing Week 2
    assigns Week 2 (not Week 1 again); the backfill is idempotent.
  - **Automation**: `Added this iteration` — `regression:missions` "An applicant already accepted before
    any mission assignment exists sees no missions (documented backfill gap)"; the week-advance half is
    `Deferred` and recorded in Known Gaps.

- **Scenario**: Mission import from Markdown
  - **Actor**: ORG_ADMIN.
  - **Steps**: on **New mission**, choose program/week/difficulty, attach a seed spec, **Import as draft**.
  - **Expected result**: a `DRAFT` mission with title and all seven content fields populated and a
    `mission.created` audit row. A file missing two sections is refused naming **both**, writing
    nothing. A non-Markdown file is refused.
  - **Automation**: `Deferred` — needs multipart upload support in the regression harness; verified in the
    portal (19 checks) and by `mission-spec.test.ts` against the real seed corpus. Recorded in Known
    Gaps.

- **Scenario**: Authorization and tenant isolation
  - **Actor**: HR / TECH_LEAD / another tenant's user.
  - **Expected result**: only ORG_ADMIN and SUPER_ADMIN manage missions and tasks; only ORG_ADMIN and TECH_LEAD
    review submissions; review history, evaluation summaries and journal lookups stay tenant-scoped.
  - **Automation**: `Added this iteration` — `regression:missions` role scenarios and `regression:tenant`
    scoping scenarios.

## Security and Data Rules

- Every new query is scoped by `tenantId`; `SubmissionReview` carries `tenantId` and cascades from
  tenant, submission and assignment.
- `@@unique([missionAssignmentId, round])` prevents duplicate rounds and guards concurrent reviews.
- Mission import: extension allow-list (`.md`/`.markdown`), 512 KB cap, always `DRAFT`, parse failures
  redirect rather than throw.
- Journal start-date rule enforced server-side on create **and** update; the picker `min` is an
  affordance only.
- Review history is append-only — never updated or deleted.
