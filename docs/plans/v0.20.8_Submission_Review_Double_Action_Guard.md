# v0.20.8 Submission Review Double-Action Guard

Code version: `v0.20.8`

Previous baseline: `v0.20.7`

Plan status: Implemented

## Summary

Once an admin reviewed a mission submission (Request changes or Repeat week), the admin portal's
review page kept the Accept / Request changes / Repeat week form visible and clickable, letting the
admin act on the same submission again and silently overwrite the prior decision (status, feedback,
rating) and re-trigger side effects (repeat-week mission creation, next-week auto-assignment,
applicant notification). This fixes both the UI gate that caused the buttons to reappear and a
related, unguarded write path in the DB layer that could let two concurrent review attempts (a
double-click, or two admin tabs) both commit.

## Scope

- Add `nextReviewerDecisions(status)` to `packages/auth/src/workflow.ts` — a reviewer-only view of
  the submission state machine that excludes the applicant's `NEEDS_REVISION → SUBMITTED`
  resubmission transition, which `nextSubmissionStatuses` incorrectly folded into the admin's
  button-visibility check.
- Gate the admin review form in
  `apps/admin/app/missions/[id]/submissions/[submissionId]/page.tsx` on
  `nextReviewerDecisions(submission.status)` instead of `nextSubmissionStatuses(...)`, and show an
  explanatory message ("Changes were requested. This section reopens once the applicant resubmits
  their evidence.") instead of rendering nothing once the form is hidden for that reason.
- Make `reviewSubmission` (`packages/db/src/submissions.ts`) write with a status-scoped
  `updateMany` + row-count guard — the same race-safe pattern its sibling `submitSubmission` already
  uses — instead of a read-then-write `update`, so a concurrent second review attempt cannot commit
  after the first has already won.

## Out of Scope

- A separate, unrelated bug in the same deadline-cadence code path (`computeMissionDeadline`
  landing on Thursday 23:59:59.999 **UTC**, which is already Friday morning in a UTC+5 timezone) is
  tracked and fixed as its own iteration, `v0.20.9`, per explicit direction to keep these two fixes
  independently versioned rather than bundled.
- Per-tenant configurable review permissions/roles — unchanged; this only fixes when the existing
  `reviewSubmissions` capability's form is shown/actionable, not who holds it.

## Test Scenarios

- **Scenario**: Admin cannot re-review a submission after requesting changes.
  **Actor**: ORG_ADMIN / TECH_LEAD reviewer.
  **Preconditions**: A `SUBMITTED` mission submission exists for an accepted applicant.
  **Steps**: Reviewer requests changes (`NEEDS_REVISION`) with feedback. Reviewer then attempts a
  second review decision (e.g. `REPEAT`) on the same submission before the applicant resubmits.
  **Expected result**: The second decision is rejected (`Invalid submission status transition`);
  the submission's status and the first decision's feedback are unchanged; the admin UI no longer
  offers the review form once status is `NEEDS_REVISION`, showing the "reopens once the applicant
  resubmits" message instead.
  **Automation**: Added this iteration (`regression:missions` — "Admin cannot re-review a submission
  after already requesting changes or a repeat week").

- **Scenario**: Accepting a submission is also terminal for further review.
  **Actor**: ORG_ADMIN / TECH_LEAD reviewer.
  **Preconditions**: A `SUBMITTED` mission submission exists for an accepted applicant.
  **Steps**: Reviewer accepts the submission with a rating. Reviewer then attempts a second review
  decision on the same (now `ACCEPTED`) submission.
  **Expected result**: The second decision is rejected the same way; portfolio/graduation evidence
  stays immutable once accepted.
  **Automation**: Added this iteration (same `regression:missions` scenario as above, second half).

- **Scenario**: Concurrent review attempts (double-click / two admin tabs) cannot both commit.
  **Actor**: ORG_ADMIN / TECH_LEAD reviewer (two overlapping requests against the same submission).
  **Preconditions**: A `SUBMITTED` mission submission.
  **Steps**: Two `reviewSubmission` calls race against the same submission id; the DB layer's
  status-scoped `updateMany` only lets the first one match `status: "SUBMITTED"`.
  **Expected result**: The second call's `updateMany` matches zero rows and the function throws
  `Invalid submission status transition`, with no `SubmissionReview` row or notification created for
  the losing call.
  **Automation**: Added this iteration (`packages/db/src/submissions.test.ts` — "guards concurrent
  review attempts with a status-scoped update (double-click / two tabs)"). Deferred at the
  regression/integration level: exercising true DB-level concurrency (two overlapping transactions)
  isn't practical in the single-threaded regression runner; the unit test proves the guard clause
  itself, and the query's race-safety follows from Postgres read-committed semantics (the same
  reasoning already relied on for `submitSubmission`'s identical pattern). Recorded as a Known Gap
  in `docs/Regression_Scenarios.md`.

- **Scenario**: A legitimate resubmission still reopens the review form.
  **Actor**: Applicant, then ORG_ADMIN / TECH_LEAD reviewer.
  **Preconditions**: A `NEEDS_REVISION` submission (from the first scenario).
  **Steps**: Applicant edits evidence and resubmits (`SUBMITTED`). Reviewer opens the submission.
  **Expected result**: `nextReviewerDecisions("SUBMITTED")` is non-empty again, so the review form
  (Accept / Request changes / Repeat week) is shown.
  **Automation**: Added this iteration (`packages/auth/src/workflow.test.ts` — "only a SUBMITTED
  submission offers reviewer decisions"); end-to-end resubmit-then-accept flow already covered by
  the pre-existing regression scenario "Submission loop: draft, submit, request changes, resubmit,
  accept — with notifications and audit" (unchanged by this iteration).

## Security and Data Rules

- No new access-control surface: the fix only narrows *when* the existing `reviewSubmissions`
  capability's action buttons/endpoint are actionable, not who can reach them.
- Tenant isolation is unchanged — `reviewSubmission` still scopes every read/write by `tenantId`.
- The atomic `updateMany` guard is a data-integrity control: it prevents a lost-update race from
  silently corrupting `Submission.status`/`reviewerFeedback`/`rating` or double-firing the
  `SubmissionReview` history, `MissionAssignment` rollup, audit log and applicant notification.
