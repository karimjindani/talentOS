# v0.20.5 Full Apprenticeship Arc And Per-Process Evidence Reports

Code version: `v0.20.5`

Previous baseline: `v0.20.4`

Plan status: Implemented

## Summary

Extends `applicant-arc.spec.ts` from a single-mission journey into the full four-week
apprenticeship arc — every week accepted, journaled, submitted and reviewed through a real
browser, week 1 still proving the revision (NEEDS_REVISION → resubmit → accepted) loop it already
covered, culminating in the real consent-and-publish flow that puts the graduate's profile on the
public portal. Replaces the single combined PDF evidence report with five separate PDFs, one per
named business process (signup/approval, mission acceptance & journal, submission & mission
acceptance, final mission & public profile, recruiter journey), redesigned to match a reference
report's structure (branded stat tiles, numbered sections, boxed step cards, a captioned
screenshot gallery) rather than the current plain step-table layout.

## Scope

- **`tests/journeys/fixtures/tenant.ts`**: `provisionJourneyTenant` publishes four missions (weeks
  1-4) in the program instead of one. `JourneyTenant.missionId` (singular) becomes
  `missionIds: string[]` (index 0 = week 1 … index 3 = week 4) — its only consumer,
  `applicant-arc.spec.ts`, is rewritten in this same iteration.
- **`tests/journeys/fixtures/types.ts`**: `StepMeta` gains a required `process` field naming which
  of the 5 business processes a step belongs to, so the PDF report can group steps by process
  instead of by journey/spec file. A shared `Process` union/constant list is the single source of
  truth for the 5 names and their order, imported by both the spec files and the report generator.
- **`tests/journeys/applicant-arc.spec.ts`** rewritten to drive all four weeks through a real
  browser: accept → (system) backdate acceptedAt → four journal entries → two task completions →
  evidence draft → (system) submit (same reachability stub already in use) → reviewer decision,
  for each week. Week 1 keeps its existing NEEDS_REVISION → applicant sees feedback → (system)
  resubmit → reviewer accepts sequence (the only week that demonstrates the revision loop, so week
  2 automatically becomes assignable via `reviewSubmission`'s existing auto-advance — see Security
  and Data Rules). Weeks 2-3 accept on the first submission. Week 4's acceptance is followed by:
  applicant reaches `/dashboard`, the consent gate now shows (`isGraduateConsentRequired`), clicks
  "I Agree & Continue" (`DashboardConsentGate` → `GraduateConsentModal`, `showProfileFormOnPublish
  = false`), and — because training is now complete — `/api/graduates/profile/acknowledge`
  auto-publishes the profile immediately (the click's own success text is transient:
  `onPublish` immediately `router.push()`es to `/dashboard/consent`, whose own status banner —
  built from the freshly-persisted `consentStatus` — is what the step actually asserts on). A
  final step reuses the applicant's own already-authenticated page to search the public
  `/graduates` directory by name and confirms the applicant's own graduate card is now listed
  there — `/api/graduates` requires no authentication at all
  (`apps/applicant/app/api/graduates/route.ts`), so this is exactly what an outside visitor would
  see regardless of whose browser context asks; a separate unauthenticated context would prove
  nothing this doesn't already. The search is load-bearing, not cosmetic: the directory is a
  public, cross-tenant listing sorted by rating at 6-per-page, so on a database with enough other
  fixtures' graduates this applicant's own profile can easily sort past page 1.
- **Process tagging**: every `journey.step()` call across `applicant-arc.spec.ts` and
  `recruiter-access.spec.ts` gets a `process` value from the shared 5-name list:
  1. Applicant Signup & Approval
  2. Mission Acceptance & Journal
  3. Submission & Mission Acceptance
  4. Final Mission & Public Profile
  5. Recruiter Journey
- **`scripts/ci/journey-pdf-report.ts`** rewritten: instead of one PDF with a page-break section
  per journey/spec file, it groups every step from every journey JSON record by `process` (order
  fixed by the shared list) and renders **one PDF per process** (5 files, numbered
  `01-`…`05-<process-slug>.pdf`). Visual redesign to match the reference report's structural
  language: an eyebrow label + title + one-line description, a stat-tile row (steps / passed /
  failed / pass rate), a note callout, and one numbered, colored-left-border step card per step
  (index badge, name, actor pill, pass/fail badge, its "proves" claim, then its screenshot or
  error text inline) — the reference's own report mixes several genuinely different content types
  per section (API request/response pairs, a UI screenshot grid, a tabular test-case sheet), so
  this adapts that *pattern* (numbered sections, boxed cards, pills/badges, stat tiles) to this
  report's single content type (one E2E step = one card) rather than forcing an artificial
  split between a "detail" and a separate "gallery" view of the same screenshots. Uses talentOS's
  own brand palette (blue `#2563eb`/navy `#1e3a8a`, the same hex values already used in
  `apps/admin/lib/email-service.ts`'s recruiter-approval email), not the reference's own unrelated
  color scheme — the reference is a structural/layout guide, not a brand asset to copy literally.
- **CI wiring**: `.github/workflows/ci.yml`'s `e2e-evidence` job and `docs/CI_CD_Pipeline.md`
  updated for 5 output files instead of 1; `npm run journeys:report:pdf` writes all 5.

## Out of Scope

- **Journeys 2 (admin authoring) and 3 (org onboarding)** — missions 2-4 are still authored via a
  direct `createMission` call in `fixtures/tenant.ts` (as week 1 already was), not through a real
  admin-authoring browser session. Unchanged from prior iterations' deferral.
- **`docs-only.spec.ts`** is unaffected — it has no natural "process" (it is a documentation
  screenshot sweep, not a business process) and keeps its own combined report entry, not one of
  the 5 per-process PDFs.
- **The `GraduateProfileForm` (bio/photo/artifacts) path** — the dashboard consent gate uses
  `showProfileFormOnPublish={false}`, so acknowledging goes straight to
  `/api/graduates/profile/acknowledge`, which auto-publishes with a placeholder bio when training
  is complete (`apps/applicant/app/api/graduates/profile/acknowledge/route.ts`). Editing the
  profile's bio/photo afterward via `/dashboard/graduate-profile` is a separate, already-untested
  surface not required to prove "publishing to the public portal" and is not added here.
- **Runtime budget**: four full weeks of real browser interaction (journal x4, tasks x2, evidence
  submission) roughly quadruples `applicant-arc`'s step count against `v0.20.4`'s single-week
  version. Expected to land well inside the existing 300s per-test Playwright timeout based on the
  single-week arc's ~28s baseline, but if it doesn't, trimming weeks 2-3's journal-entry count
  below 4 is explicitly out of scope for this plan (4 is the real readiness-gate minimum — see
  `packages/db/src/submissions.ts` — so a trimmed count wouldn't reach ACCEPTED anyway) — the
  actual fallback would be revisiting scope, not silently shortening the arc.

## Test Scenarios

### 1. An applicant completes all four apprenticeship missions through a real browser session and their profile publishes to the public portal

- **Scenario**: An applicant completes all four apprenticeship missions through a real browser
  session and their profile publishes to the public portal
- **Actor**: prospective applicant, then accepted applicant; org admin (reviewer)
- **Preconditions**: a fresh journey-scoped tenant with four published missions (weeks 1-4)
- **Steps**: sign up → apply → org admin accepts → for each of weeks 1-4: accept mission → write 4
  journal entries → complete 2 mission tasks → submit evidence → org admin reviews (week 1: first
  requests changes, applicant resubmits, then accepted; weeks 2-4: accepted on first submission) →
  after week 4's acceptance, applicant reaches `/dashboard`, the consent gate appears, applicant
  agrees → profile auto-publishes (training complete) → searching the public `/graduates`
  directory by name confirms the graduate now appears there
- **Expected result**: all steps pass; `GraduateProfile.publicProfileEnabled` is `true`; the
  applicant's card renders on the public, unauthenticated `/graduates` page; every step captures a
  full-page screenshot as evidence
- **Automation**: Added this iteration — `tests/journeys/applicant-arc.spec.ts`
  (`npm run journeys:applicant`)

### 2. Journey evidence is produced as one PDF per named business process, not one combined report

- **Scenario**: Journey evidence is produced as one PDF per named business process
- **Actor**: PR reviewer / the CI system itself
- **Preconditions**: the `e2e-evidence` job running on a pull request, with both journeys' JSON
  results present
- **Steps**: `journeys:report:pdf` reads every journey JSON record, groups all steps (from both
  `applicant-arc` and `recruiter-access`) by their `process` tag, and renders one PDF per process
- **Expected result**: 5 PDF files are produced (`01-applicant-signup-approval.pdf` …
  `05-recruiter-journey.pdf`), each containing only that process's steps, in step order, with a
  stat-tile summary and screenshot gallery; a well-formed (if near-empty) set is still produced
  when the stack never booted or a journey failed partway (matching the existing non-throwing
  `if: always()` contract)
- **Automation**: Added this iteration — `.github/workflows/ci.yml` (`Write journey PDF report`
  step), `scripts/ci/journey-pdf-report.ts`

### Tenant isolation

Unchanged from `v0.20.3`/`v0.20.4`: the journey harness provisions a fully isolated tenant per run
and per-actor browser contexts. The new unauthenticated-context step (confirming public visibility)
does not introduce a new tenant-scoped data path — graduate profiles are deliberately public and
cross-tenant-discoverable by design, per `v0.20.3`'s plan.

## Security and Data Rules

- Week 1's revision loop is preserved exactly (NEEDS_REVISION with reviewer feedback, applicant
  sees it, resubmission) — this iteration adds a resubmit-then-accept tail to it rather than
  replacing it, so the existing `v0.20.3` proof (immutable `SubmissionReview` history) is not lost.
- Weeks 2-4 are auto-assigned by `reviewSubmission`'s existing auto-advance
  (`packages/db/src/submissions.ts`: `weekNumber < FINAL_PROGRAM_WEEK` triggers
  `assignWeekMissionToAcceptedApplicantTx`) — no new assignment logic is added by this iteration;
  the journey proves existing behavior end-to-end for the first time.
- The public-visibility assertion reuses the applicant's own authenticated page rather than a
  second `BrowserContext`: `/api/graduates` requires no authentication at all and does not branch
  on session state, so a separate context would prove nothing a shared one doesn't already —
  verified directly by reading that route before relying on it.
- The applicant's Keycloak `lastName` is run-scoped (`Applicant <runId>`), not the fixed literal
  "Applicant" every prior run used — this journey is the first to publish a *public, cross-tenant*
  profile from this fixture, and a literal duplicate name across runs would both pollute the shared
  directory and make this journey's own final assertion ambiguous against another run's
  identically-named card.
- The applicant's Prisma `User` row (and its `TenantMembership`) is now explicitly marked for
  regression cleanup once it exists (previously unmarked entirely — harmless before this
  iteration, since no journey ever published a profile from it, but a real leak now: 28 orphaned
  applicant `User` rows, several with already-published `GraduateProfile`s, had accumulated in the
  local database before this fix was found and applied).
- `RecruiterAccessRequest` joins `RegressionDataMarker`'s tracked entity types
  (`packages/db/src/regression.ts`), for the same class of reason `RecruiterAccount` did in
  `v0.20.3` (D-103): `/api/graduates/request-access` attaches every request to "the first public
  graduate profile" in the whole database, not necessarily one the requesting run owns, so relying
  on cascade from that graduate's own cleanup silently orphans the request row whenever some other
  fixture's graduate happens to be "first" — found live via `recruiter-access.spec.ts` once the
  local database held more than one published graduate.
- **Observed, not fixed**: `/api/graduates/profile/acknowledge`'s placeholder-profile path sets
  `overallRating: 0` unconditionally, unlike `createOrUpdateGraduateProfile` (which computes the
  real average from `getCompletionSnapshot`). A profile published through the dashboard consent
  gate alone (no `GraduateProfileForm` submission) therefore shows "0.0" in the public directory
  even though the applicant has four real reviewer ratings. This is existing behavior this
  iteration's journey makes visible for the first time, not a regression it introduces — recorded
  in `Regression_Scenarios.md` Known Gaps rather than silently fixed, since changing it is an
  app-behavior decision outside a test-coverage iteration's scope.
