# v0.20.7 Applicant Profile Photo, Apply Page Redesign, And Graduate-Profile Defaults Carry-Through

Code version: `v0.20.7`

Previous baseline: `v0.20.6`

Plan status: Implemented

## Summary

Applicants can now optionally upload a profile photo when they apply, alongside a redesigned
apply page (icons instead of emoji, a real drag-and-drop CV dropzone, a circular avatar upload
with live preview). That photo — along with the GitHub/LinkedIn URLs already collected at apply
time — now carries through automatically as the default photo/links on the graduate's public
profile the first time one is created (on consent decline, skip, or acknowledge), instead of the
graduate having to re-enter the same information from scratch at graduation.

## Scope

- `User.avatarFileId` (new, unique, nullable `StoredFile` relation) — an applicant's own profile
  photo, distinct from `GraduateProfile.profilePhotoFileId` which only exists post-graduation.
- `apps/applicant/app/apply/page.tsx`: `submitApplication` accepts an optional `photo` field,
  validated the same way `apps/applicant/app/api/graduates/profile/photo/route.ts` already
  validates graduate photos (JPEG/PNG/WebP, 2 MB cap, magic-byte signature check), stored and
  linked via the new `setUserAvatar()`.
- `apps/applicant/app/apply/ApplyUploadFields.tsx` (new): circular avatar upload (live preview,
  remove button, client-side type/size feedback) and a CV dropzone (drag-and-drop, drag-over
  state, selected-file confirmation) — both replace plain native `<input type="file">` elements.
- Visual redesign of the rest of the apply page: `lucide-react` icons replace emoji glyphs,
  reusing the existing tenant-brand token system (`brand-blue`/`brand-navy`/`brand-mist` are
  per-tenant CSS variables — no new fixed palette or fonts).
- `packages/db/src/graduates.ts`: new `getGraduateProfileDefaults(userId)` — reads the applicant's
  most recent accepted `Application`'s `githubUrl`/`linkedinUrl` and their `User.avatarFileId`.
  Wired into `declineGraduateProfilePublishing`, `skipGraduateConsent` (both in `graduates.ts`),
  and the `acknowledge` route (`apps/applicant/app/api/graduates/profile/acknowledge/route.ts`) —
  applied only when a `GraduateProfile` is created for the first time, never on an update.
- `packages/db/src/users.ts`: new `setUserAvatar(userId, avatarFileId)`.

## Out of Scope

- **Storage browser upload/download regression scenario** (the pre-existing documented skip in
  `scripts/regression/run.ts`'s `storage` area) — considered for this iteration but not picked up;
  still an open gap, unchanged by this iteration.
- **`GraduateProfileForm` pre-fill on edit** — `GraduateConsentModal.tsx` renders
  `GraduateProfileForm` with no `initialData` prop at all, so a graduate opening the edit form
  after this iteration still sees blank fields even though their carried-over photo/links are
  already saved and live on their public profile. Pre-existing gap, not introduced by this
  iteration, and not closed by it — noted here so it isn't mistaken for something this iteration
  was supposed to fix.
- Carrying defaults into an *existing* `GraduateProfile` (e.g. backfilling a graduate who
  published before this iteration) — deliberately out of scope; defaults only apply at creation
  time, to avoid silently overwriting a graduate's own edits (see S5 below).

## Test Scenarios

- **Scenario**: Applicant uploads an optional profile photo at apply time.
  - **Actor**: Authenticated new applicant.
  - **Preconditions**: A published program exists for the tenant.
  - **Steps**: Open `/apply`, fill motivation, upload a valid CV (PDF) and a valid photo
    (JPEG/PNG/WebP, under 2 MB) via the new avatar upload control, submit.
  - **Expected result**: Application is created; a `StoredFile` (category `profile-photo`,
    status `READY`) is created and linked via `User.avatarFileId`; redirect to `/application`.
  - **Automation**: Deferred — verified manually this iteration via a real Chromium browser
    (Playwright) end-to-end: filled the live form, uploaded a real CV and photo, submitted, and
    confirmed `avatarFileId` was linked in the database. Not added to `scripts/regression/run.ts`
    because that suite calls `packages/db` functions directly and does not exercise the Next.js
    page/server-action layer where this validation lives — the same boundary the pre-existing CV
    upload validation in this same file has always sat at (also untested by the regression
    suite). Recorded as a Known Gap in `Regression_Scenarios.md` alongside that CV precedent
    rather than introducing an inconsistent extra layer of rigor for only the new field.

- **Scenario**: An invalid profile photo is rejected server-side.
  - **Actor**: Authenticated new applicant.
  - **Preconditions**: Same as above.
  - **Steps**: Submit the apply form with a non-image file (or an oversized image) selected as
    the photo field — bypassing the client-side `accept`/size hints (e.g. via a direct POST).
  - **Expected result**: `submitApplication` throws before any upload or `User` mutation happens;
    no orphan `StoredFile` row, no partial application.
  - **Automation**: Deferred, same reasoning as above — code-reviewed against the identical
    validation order already used by `graduates/profile/photo/route.ts` (type check, size check,
    magic-byte signature check, all before any write).

- **Scenario**: A brand-new graduate profile inherits GitHub/LinkedIn and avatar from the
  applicant's accepted application.
  - **Actor**: System (triggered by consent decline/skip/acknowledge).
  - **Preconditions**: Applicant has an `ACCEPTED` application with `githubUrl`/`linkedinUrl` set,
    and a `User.avatarFileId` pointing at a `READY` image `StoredFile`. No `GraduateProfile` row
    exists yet for this user.
  - **Steps**: Call `skipGraduateConsent(userId)` (or `declineGraduateProfilePublishing` /
    the `acknowledge` route — all three share `getGraduateProfileDefaults`).
  - **Expected result**: The newly created `GraduateProfile` has `githubUrl`, `linkedinUrl`, and
    `profilePhotoFileId` all equal to the applicant's apply-time values.
  - **Automation**: Added this iteration — `regression:public-portal`, "A brand-new graduate
    profile inherits GitHub/LinkedIn and avatar from the applicant's accepted application
    (v0.20.7)".

- **Scenario**: A graduate profile created with no accepted application or avatar gets null
  defaults, not a crash.
  - **Actor**: System.
  - **Preconditions**: Applicant has no `githubUrl`/`linkedinUrl` on any accepted application and
    no `avatarFileId`.
  - **Steps**: Call `declineGraduateProfilePublishing(userId)` for the first time.
  - **Expected result**: `getGraduateProfileDefaults` returns `{ githubUrl: null, linkedinUrl:
    null, profilePhotoFileId: null }`; the created profile has the same nulls — no fabricated
    values, no error.
  - **Automation**: Added this iteration — `regression:public-portal`, "A graduate profile
    created with no accepted application or avatar gets null defaults, not a crash (v0.20.7)".

- **Scenario**: Apply-time defaults are only applied on first creation — an existing profile's
  photo and links are never overwritten.
  - **Actor**: System.
  - **Preconditions**: A `GraduateProfile` already exists with its own `githubUrl`/`linkedinUrl`
    (e.g. the graduate edited them via `GraduateProfileForm`). The applicant's `Application`
    later gains *different* `githubUrl`/`linkedinUrl` values.
  - **Steps**: Call `declineGraduateProfilePublishing(userId)` again.
  - **Expected result**: The existing profile's `githubUrl`/`linkedinUrl` are unchanged — the
    newer, different apply-time values never overwrite them, because
    `getGraduateProfileDefaults` is only consulted on the create branch, never the update branch.
  - **Automation**: Added this iteration — `regression:public-portal`, "Apply-time defaults are
    only applied on first creation — an existing profile's photo and links are never overwritten
    (v0.20.7)".

No new authorization/role surface was introduced — the apply page's existing "must be
authenticated" gate (pre-existing `PROTECTED_PREFIXES` middleware) already covers the new photo
field, since it's just another `FormData` field on the same protected `submitApplication` action.
No tenant-crossing surface was introduced either: `getGraduateProfileDefaults` takes a `userId`
the caller has already tenant-resolved (same as every other function in `graduates.ts`), and its
own `Application`/`User` lookups are scoped to that single user, not tenant-wide queries.

## Security and Data Rules

- Photo upload validation mirrors the existing graduate-photo route exactly: content-type
  allowlist (`image/jpeg`, `image/png`, `image/webp`), 2 MB size cap, and a magic-byte signature
  check (`hasValidImageSignature`) so a renamed non-image file is rejected even if its declared
  MIME type is spoofed.
- `getGraduateProfileDefaults` only reads data the same user already owns (their own accepted
  `Application`, their own `User.avatarFileId`) — no cross-user or cross-tenant read.
- Defaults are applied strictly on `GraduateProfile` creation, never on update, so a graduate's
  own later edits (via `GraduateProfileForm`) are never silently clobbered by this mechanism.
