# v0.20.3 Journey E2E Evidence Pipeline And Public-Portal Fixes

Code version: `v0.20.3`

Previous baseline: `v0.20.2`

Plan status: Implemented

## Summary

Delivers a Playwright-driven, multi-actor "journey" E2E test suite that exercises real browser
sessions through the applicant and admin portals end to end (not just HTTP/DB-level assertions),
wired into CI to produce evidence — JSON, per-step screenshots, a Markdown step summary, and a
combined PDF report with the screenshots embedded — as a reviewable, shareable artifact on every
pull request. Alongside this, hardens the public-portal graduate-consent and recruiter-access-request
flows that shipped in the prior graduate-portal merge (PR #62, unreleased-version work absorbed into
`main` ahead of this baseline): fixes a bug where declining or skipping consent silently failed to
persist for an applicant who had never created a graduate profile, and closes the resulting
regression-coverage gap (the `public-portal` area grows from 1 scenario to 6, including the full
recruiter approve→verify→access→revoke lifecycle).

## Scope

- **`tests/journeys/` Playwright suite** (built earlier in this same development session, prior to
  this document, per `docs/designs/2026-08-13-journey-e2e-implementation-plan.md`):
  - `fixtures/journey.ts` — a shared fixture provisioning a fully isolated tenant per run
    (`jrn-<runId>.lvh.me`), per-actor browser contexts, step-level screenshot capture written to
    `.ops/journey-evidence/<journey>/<runId>/`, and multi-stage teardown (DB transaction cleanup,
    direct Keycloak user deletion, a 24h orphan sweep for runs killed mid-flight).
  - `applicant-arc.spec.ts` — a 13-step journey: applicant signup, apply, org-admin acceptance,
    mission acceptance, mission tasks, journal entry, evidence submission, admin review, and dashboard
    verification.
  - `docs-only.spec.ts` — 7 test blocks covering public pages, the apply flow, the applicant dashboard
    and working flows, the admin portal and its authoring/review flows, and the Ops console; replaces
    the retired `scripts/user-guide/capture-screenshots.ts` (deleted this session), which photographed
    pages but asserted nothing.
- **CI wiring** (`.github/workflows/ci.yml`, `e2e-evidence` job): runs the journeys after the scenario
  suite (`Run journeys`), renders a Markdown step summary and a per-journey `evidence.md`
  (`scripts/ci/journey-report.ts`, `Write journey evidence`), renders a single combined PDF with every
  journey's step table and embedded screenshots via Playwright's already-installed Chromium
  (`scripts/ci/journey-pdf-report.ts`, `Write journey PDF report` — new this iteration), and uploads
  all of it as the `e2e-evidence-<run number>` artifact.
- **Consent-persistence fix** (`packages/db/src/graduates.ts`,
  `apps/applicant/app/api/graduates/profile/{decline,skip}/route.ts`): `declineGraduateProfilePublishing`
  and `skipGraduateConsent` now create a placeholder `GraduateProfile` row when none exists yet,
  mirroring the placeholder-creation path `createOrUpdateGraduateProfile` (acknowledge) already had.
  Previously both threw `"No graduate profile exists to decline/skip"`, and the API route caught that
  by silently returning `{success: true}` without writing anything — the applicant saw a success
  message but the decision was lost on the next page load.
- **5 new `public-portal` regression scenarios** (`scripts/regression/run.ts`, area grows from 1
  scenario to 6): decline/skip persistence with no prior profile (the bug-fix regression case), decline
  unpublishing an already-public profile, and the full recruiter lifecycle (create → PENDING refuses
  access → approve → verify → appears in every published graduate's directory + full portfolio →
  reusable within its window → revoke → access removed everywhere → revoked token refused) plus
  pending/rejected-token refusal with the rejection reason surfaced.
- **Regression-harness gap closed** (`packages/db/src/regression.ts`): `RecruiterAccount` added as a
  tracked, swept `RegressionDataMarker` entity type. It has no relation back to `User`/`Tenant`, so
  nothing in the existing cleanup chain could ever reach it — every regression run touching the
  recruiter flow would have leaked one row into the database forever.
- **48 new unit tests** for `packages/db/src/graduates.ts` — previously untested despite holding all
  consent, eligibility, and recruiter approve/verify/revoke business logic.
- **`.claude/skills/` tracked in git**, `.gitignore` narrowed from a blanket `.claude/` ignore to just
  `.claude/settings.local.json` — the project-specific skills (`fresh-local-run`,
  `ssdlc-documentation`, `version-allocation-and-gates`) encode this repo's own workflows and should be
  shared, not treated as personal config.
- **Dead admin nav item removed** (`apps/admin/components/SidebarNav.tsx`): the Operations page had
  been removed at some earlier point, but the sidebar's `/operations` link was never cleaned up, so
  it sat in the nav pointing to a route with no page component. Found live during this iteration's
  own browser verification of the admin portal.
- **Journey-suite hang fixed** (`tests/journeys/fixtures/actors.ts`, `applicant-arc.spec.ts`,
  `docs-only.spec.ts`): found live while gathering this iteration's own verification evidence — every
  `page.waitForLoadState("networkidle")` call site was unbounded, and a Chromium/CDP dedup quirk on
  next-auth's duplicate mount/refetch-on-focus session fetch could leave Playwright's own
  pending-request ledger permanently off by one, hanging the affected step until the whole test's
  budget ran out. All three call sites are now bounded to 5s with the rejection swallowed. See `D-103`.

- **Journeys 2 (admin authoring) and 3 (org onboarding + team collaboration)** from the original

- **A second, independent implementation of E2E-evidence PDF reporting** was built concurrently on
  `feature/e2e-evidence-pipeline` (PR #67) by another contributor, using a different architecture
  (screenshot-capture-driven rather than Playwright-journey-driven, with PII masking). That PR was
  closed unmerged before this baseline was allocated; its approach is not reconciled with this one.
  See Known Gaps.
- **3 docs-only screenshots remain `test.fixme()`** (applicant-work-in-progress views) — the seeded

  assignment, so there is no representative "in progress" state to photograph without fabricating data
  or mutating seed state that 58 other regression scenarios depend on. A seed-data fix is its own
  iteration.

## Test Scenarios

### 1. Applicant completes the full apprenticeship arc through a real browser session

- **Scenario**: Applicant completes the full apprenticeship arc through a real browser session
- **Actor**: prospective applicant, then accepted applicant; org admin (reviewer)
- **Preconditions**: a fresh journey-scoped tenant is provisioned for the run
  (`jrn-<runId>.lvh.me`), with the org-admin identity provisioned in Keycloak and granted realm roles
- **Steps**: sign up → verify email → apply to the program → org admin accepts the application →
  applicant accepts the Week 1 mission → completes the two prerequisite mission tasks → writes a
  journal entry → drafts and submits evidence → org admin reviews and accepts the submission →
  applicant's dashboard reflects the accepted state
- **Expected result**: all 13 steps pass, each capturing a full-page screenshot as evidence; the run
  leaves zero residual database or Keycloak state on success
- **Automation**: Added this iteration — `tests/journeys/applicant-arc.spec.ts`
  (`npm run journeys:applicant`)

### 2. Every reachable portal surface renders and is captured for the illustrated user guide

- **Scenario**: Every reachable portal surface renders and is captured for the illustrated user guide
- **Actor**: anonymous visitor, applicant, admin, ops operator
- **Preconditions**: the seeded demo tenant
- **Steps**: navigate public pages, the apply flow, the applicant dashboard and its working flows, the
  admin portal and its authoring/review flows, and the Ops console
- **Expected result**: 7 test blocks pass; screenshots land in the same evidence directory structure
  as the applicant-arc journey (`.ops/journey-evidence/docs-only/<runId>/`)
- **Automation**: Added this iteration — `tests/journeys/docs-only.spec.ts` (`npm run journeys:docs`)

### 3. Journey evidence (JSON, screenshots, Markdown, and a combined PDF) is produced in CI and uploaded as a reviewable artifact

- **Scenario**: Journey evidence (JSON, screenshots, Markdown, and a combined PDF) is produced in CI
  and uploaded as a reviewable artifact
- **Actor**: PR reviewer / the CI system itself
- **Preconditions**: the `e2e-evidence` job running on a pull request
- **Steps**: journeys run after the scenario suite; results are rendered to the step summary and to a
  single PDF with every journey's step table and embedded screenshots
- **Expected result**: a well-formed PDF artifact is produced even when the Docker stack never booted
  (graceful "no evidence" path, exits 0, writes nothing) or a journey step failed (evidence is written
  before teardown runs, and the failed step's error text appears in the report instead of a
  screenshot)
- **Automation**: Added this iteration — `.github/workflows/ci.yml` (`Write journey PDF report` step),
  `scripts/ci/journey-pdf-report.ts`

### 4. Declining consent before a graduate profile ever existed still persists the decision (the bug fix)

- **Scenario**: Declining consent before a graduate profile ever existed still persists the decision
- **Actor**: accepted applicant who is eligible (four accepted, rated missions) but has never
  acknowledged consent before — no `GraduateProfile` row exists yet
- **Preconditions**: none beyond eligibility — this is exactly the state every first-time-eligible
  applicant is in
- **Steps**: applicant clicks "Decline" on the consent modal
- **Expected result**: a `GraduateProfile` row is created with `consentStatus=DECLINED`,
  `publicProfileEnabled=false`; the profile is not publicly discoverable; a `ConsentHistory` row
  records the decision. Before this fix: silent no-op — the API returned `{success:true}`, nothing was
  written, and the consent modal reappeared on the next page load as if nothing had happened.
- **Automation**: Added this iteration — `regression:public-portal`
  ("Declining consent before a graduate profile ever existed still persists the decision
  (D-consent-persist)"); `packages/db/src/graduates.test.ts`

### 5. Skipping consent before a graduate profile ever existed still persists the decision

- **Scenario**: Skipping consent before a graduate profile ever existed still persists the decision
- **Actor**: same as above, choosing "Skip for Now" instead of "Decline"
- **Preconditions**: same as above
- **Steps**: applicant clicks "Skip for Now"
- **Expected result**: `consentStatus=SKIPPED` persists to a new `GraduateProfile` row; the profile is
  not publicly discoverable
- **Automation**: Added this iteration — `regression:public-portal`
  ("Skipping consent before a graduate profile ever existed still persists the decision
  (D-consent-persist)"); `packages/db/src/graduates.test.ts`

### 6. An approved recruiter access request is verified, grants access to every published graduate, and revocation removes it everywhere

- **Scenario**: An approved recruiter access request is verified, grants access to every published
  graduate profile, and revocation removes it everywhere
- **Actor**: recruiter (an unauthenticated public visitor submitting a form — recruiters are not
  tenant members); ORG_ADMIN reviewer
- **Preconditions**: a published, consented graduate profile exists
- **Steps**: recruiter submits an access request → the still-PENDING request cannot be verified →
  admin approves it → recruiter verifies the emailed token → a session is granted, and the recruiter
  sees every published graduate (not only the one the original request named) plus the full
  mission-evidence portfolio for each → admin revokes the request → the recruiter's access is removed
  everywhere → the revoked token can no longer be verified
- **Expected result**: every state transition matches; revocation is total (both the directory listing
  and the individual portfolio view), not partial
- **Automation**: Added this iteration — `regression:public-portal`
  ("An approved recruiter access request is verified, grants access to every published graduate, and
  revocation removes it"); `packages/db/src/graduates.test.ts`
  (`consumeRecruiterAccessToken`, `getAllAccessibleGraduates`, `getFullProfileForRecruiter`,
  `revokeAccessRequest`)

### 7. Pending and rejected recruiter access requests cannot be verified, and the rejection reason reaches the recruiter

- **Scenario**: Pending and rejected recruiter access requests cannot be verified, and the rejection
  reason reaches the recruiter
- **Actor**: recruiter
- **Preconditions**: two access requests exist for the same published graduate — one left PENDING,
  one an admin has REJECTED with a stated reason
- **Steps**: recruiter attempts to verify the PENDING request's token; recruiter attempts to verify
  the REJECTED request's token
- **Expected result**: both refuse access (no session is granted); the rejected case surfaces the
  admin's stated rejection reason back to the recruiter rather than a generic failure
- **Automation**: Added this iteration — `regression:public-portal`
  ("Pending and rejected recruiter access requests cannot be verified, and the rejection reason
  reaches the recruiter"); `packages/db/src/graduates.test.ts`

### Tenant isolation

The journey suite provisions a fully isolated tenant per run (`jrn-<runId>.lvh.me`) with its own
Keycloak realm-role assignment — itself a tenant-isolation property of the harness, verified by the
zero-residual-state assertion in Scenario 1 and by concurrent-run non-collision (evidence directories
are `runId`-namespaced, proven incidentally across the several journey runs executed during this
iteration's own verification). The public-portal consent/recruiter work does not introduce a new
tenant-scoped data path to test in isolation: graduate profiles are deliberately public and
cross-tenant-discoverable by design (a public directory, not a tenant-scoped resource), and recruiters
are not tenant members at all. Noted explicitly per the plan template's "if applicable" clause rather
than forcing a scenario that does not fit the feature's actual data model.

## Security and Data Rules

- Recruiter access tokens are never stored in plaintext — only `hashToken(rawToken)` is persisted
  (`packages/db/src/token-generator.ts`); a dedicated unit test asserts the persisted `token` field on
  creation never equals the raw value handed to the recruiter.
- The consent API layer must not silently swallow a write failure into a fake success response — this
  is exactly the class of defect this iteration fixes, and the regression/unit coverage added
  specifically guards against its reintroduction.
- Journey-provisioned Keycloak identities and database rows are fully reaped in teardown via three
  independent stages (Prisma transaction cleanup, direct Keycloak user deletion, and a 24h orphan
  sweep for runs killed before reaching teardown) — verified this iteration by marker-count checks,
  direct Keycloak realm queries, and cross-run evidence-directory non-collision.
- `RecruiterAccount` rows created by regression scenarios are now swept by `cleanupRegressionData` —
  previously an unbounded per-run leak for any scenario touching the recruiter flow.
