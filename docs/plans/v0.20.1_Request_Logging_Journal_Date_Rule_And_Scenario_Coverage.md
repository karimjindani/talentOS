## Summary

`v0.20.1` follows `v0.20.0` with three unrelated threads: an observability aid (request logging in
both app middlewares), a product rule change to the Engineering Journal (uniqueness moves from one
entry per applicant per calendar date to one per applicant **per mission** per calendar date), and a
substantial expansion of end-to-end scenario coverage — 12 new scenarios in `scripts/regression/run.ts`
covering the review lifecycle, cross-tenant isolation, the deadline sweep, terminal assignment states,
and portal/client separation. It also repairs two CI-only screenshot-capture defects exposed once the
`e2e-evidence` job (`v0.20.1`, PR #57) started running the capture on a fresh seeded database.

## Scope

- **Request logging.** Both app middlewares log method, path, tenant and auth state to stdout.
- **Journal per-mission-per-date uniqueness.** Migration
  `20260811000000_v0_20_1_journal_per_mission_per_date` drops the
  `(tenantId, applicantId, entryDate)` unique index and replaces it with
  `(tenantId, applicantId, missionId, entryDate)`; `assertEntryDateAvailable` takes `missionId` on both
  the create and update paths, and the conflict messages name the mission.
- **Scenario coverage.** 12 new runner scenarios (3 `admin`, 3 `tenant`, 3 `missions`, 2 `auth`,
  1 `journal` replacing the superseded per-date scenario), taking `run.ts` from 42 to **53** scenario
  objects.
- **Unit coverage.** New tests for the AI mentor API route, `CollapsibleTask`, `CountdownTimer`,
  `DeadlineCountdown`, plus `evaluation.test.ts` and `mission-spec.test.ts` against the `v0.20.0`
  modules, and extensions to nine existing suites.
- **CI capture fixes.** `seed-dashboard.ts` supplies the now-required `ProgramTask.missionId`;
  `capture-screenshots.ts` uses the seeded accepted applicant for workflow shots and skips Ops-console
  shots gracefully when that console is not reachable.

## Out of Scope

- Making request logging configurable — shipped unconditional and corrected in `v0.20.2` (`D-102`).
- Structured/JSON log output and log shipping: stdout plus `docker compose logs` is enough for local
  work, and no log aggregation target exists yet.
- Backfilling journal entries: the new index is strictly weaker than the old one, so every existing
  row remains valid and no data migration is needed.

## Test Scenarios

Automated scenario names are copied verbatim from `scripts/regression/run.ts`.

- **Scenario**: One journal entry per applicant per mission per calendar date is enforced.
  - **Actor**: Accepted applicant.
  - **Preconditions**: Applicant assigned to two missions, both started on or before the entry date.
  - **Steps**: Create a journal entry dated today against mission A; create a second entry dated today
    against mission B; then attempt a third entry dated today against mission A again.
  - **Expected result**: The first two succeed — the same date across different missions is now legal.
    The third is rejected with `JournalEntryDateConflictError` and a message naming the mission.
  - **Automation**: `Added this iteration` — `regression:journal`. Replaces the superseded per-date
    scenario.

- **Scenario**: Reviewer can request revisions and applicant can resubmit (v0.20.1).
  - **Actor**: `TECH_LEAD` reviewer, then the accepted applicant.
  - **Preconditions**: A submitted submission awaiting review.
  - **Steps**: Reviewer records a `NEEDS_REVISION` decision with feedback; the applicant edits the
    submission and resubmits.
  - **Expected result**: The assignment returns to a submittable state, the resubmission is accepted,
    and the revision count increments.
  - **Automation**: `Added this iteration` — `regression:admin`.

- **Scenario**: Reviewer can reject with REPEAT and a new attempt is created (v0.20.1).
  - **Actor**: `TECH_LEAD` reviewer.
  - **Preconditions**: A submitted submission awaiting review.
  - **Steps**: Reviewer records a `REPEAT` decision with feedback.
  - **Expected result**: A new attempt is created for the applicant with an incremented attempt number;
    the prior attempt's record is retained rather than overwritten.
  - **Automation**: `Added this iteration` — `regression:admin`.

- **Scenario**: Review writes immutable SubmissionReview history record (v0.20.1).
  - **Actor**: `TECH_LEAD` reviewer.
  - **Preconditions**: A submitted submission awaiting review (`v0.20.0`, `D-098`).
  - **Steps**: Record a review decision, then record a second decision on a later round.
  - **Expected result**: Each decision appends a `SubmissionReview` row with its own round number; no
    earlier row is mutated or deleted.
  - **Automation**: `Added this iteration` — `regression:admin`.

- **Scenario**: Cross-tenant submission access is denied via getTenantSubmission (v0.20.1).
  - **Actor**: An admin of tenant B.
  - **Preconditions**: A submission owned by tenant A.
  - **Steps**: Request tenant A's submission while scoped to tenant B.
  - **Expected result**: Denied — no submission is returned. The tenant scope is enforced in the query,
    not in the UI.
  - **Automation**: `Added this iteration` — `regression:tenant`.

- **Scenario**: Cross-tenant journal review lookup is denied (v0.20.1).
  - **Actor**: An admin of tenant B.
  - **Preconditions**: Journal entries owned by an applicant of tenant A.
  - **Steps**: Look up tenant A's journal entries while scoped to tenant B.
  - **Expected result**: Denied — no entries are returned.
  - **Automation**: `Added this iteration` — `regression:tenant`.

- **Scenario**: Cross-tenant mission visibility is rejected (v0.20.1).
  - **Actor**: A user of tenant B.
  - **Preconditions**: A mission owned by tenant A.
  - **Steps**: Request tenant A's mission while scoped to tenant B.
  - **Expected result**: Rejected — the mission is not visible.
  - **Automation**: `Added this iteration` — `regression:tenant`.

- **Scenario**: Deadline sweep marks overdue assignments and disqualifies after grace (v0.20.1).
  - **Actor**: The scheduled Ops deadline sweep.
  - **Preconditions**: One assignment past its deadline but inside grace; one past its grace end.
  - **Steps**: Run the sweep.
  - **Expected result**: The first is marked overdue; the second is disqualified. Assignments inside
    their deadline are untouched.
  - **Automation**: `Added this iteration` — `regression:missions`.

- **Scenario**: Deadline sweep is idempotent — running twice produces no new changes (v0.20.1).
  - **Actor**: The scheduled Ops deadline sweep.
  - **Preconditions**: A sweep has already run over the same data.
  - **Steps**: Run the sweep a second time with no intervening change.
  - **Expected result**: No further state transitions and no duplicate notifications — a retried or
    double-scheduled sweep is safe.
  - **Automation**: `Added this iteration` — `regression:missions`.

- **Scenario**: FAILED assignment rejects new submissions (v0.20.1).
  - **Actor**: An applicant whose assignment is `FAILED`.
  - **Preconditions**: Assignment in the terminal `FAILED` state.
  - **Steps**: Attempt to submit against it.
  - **Expected result**: Rejected — a terminal state cannot accept new work.
  - **Automation**: `Added this iteration` — `regression:missions`.

- **Scenario**: Applicant and admin portals use separate Keycloak clients (v0.20.1).
  - **Actor**: Unauthenticated visitor to each portal.
  - **Preconditions**: Realm imported with both clients.
  - **Steps**: Begin the login flow on each portal and inspect the resulting authorization request.
  - **Expected result**: Each portal drives its own client ID; neither borrows the other's.
  - **Automation**: `Added this iteration` — `regression:auth`.

- **Scenario**: Applicant session cookie does not grant admin portal access (v0.20.1).
  - **Actor**: An authenticated applicant.
  - **Preconditions**: A valid applicant session on the applicant portal.
  - **Steps**: Present that session to the admin portal.
  - **Expected result**: Denied — the admin middleware redirects to `/forbidden` rather than admitting
    an `APPLICANT` role. This is the role-denial case for the iteration.
  - **Automation**: `Added this iteration` — `regression:auth`.

- **Scenario**: Request logging reaches container stdout without altering responses.
  - **Actor**: Any visitor to either portal.
  - **Preconditions**: Local Docker stack running.
  - **Steps**: Load a page on each portal, then read `docker compose logs applicant admin`.
  - **Expected result**: One line per request carrying method, path, tenant and auth state; the
    response itself is unchanged.
  - **Automation**: `Deferred` — the runner asserts on HTTP responses and database state, not on
    container stdout, and has no log-capture helper. Recorded as a Known Gap in
    `docs/Regression_Scenarios.md`. `v0.20.2` adds unit coverage of the enable rule, the path filter
    and the formatter (`packages/auth-web/src/request-log.test.ts`), which is where the logic now lives.

## Security and Data Rules

- The three cross-tenant scenarios assert isolation at the data-access layer, not the UI.
- The journal index change is strictly weaker than its predecessor: every row valid under
  `(tenantId, applicantId, entryDate)` is valid under `(tenantId, applicantId, missionId, entryDate)`,
  so the migration cannot orphan or reject existing data.
- Request logging records path, tenant slug and a boolean auth flag. It does not record user
  identifiers, session tokens, query strings or request bodies.
