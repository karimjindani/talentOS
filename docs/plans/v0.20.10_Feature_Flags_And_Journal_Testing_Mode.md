# v0.20.9 Feature Flags And Journal Testing Mode

Code version: `v0.20.10`

Previous baseline: `v0.20.8`

Plan status: Implemented

## Summary

Adds a DB-backed feature flag system controllable from the Ops console, with the first flag (`journal.testing_mode`) relaxing journal entry restrictions for local testing. When enabled, journal entries can be created/edited without the one-per-mission-per-date, no-future-date, no-before-mission-start, and locked-after-submission restrictions, and the submission readiness gate no longer requires 4 journal entries. This lets testers exercise the full mission submission flow without waiting for real calendar dates.

## Scope

- **FeatureFlag model** (`schema.prisma`): new `FeatureFlag` table (key, enabled, description, timestamps). Migration creates the table and drops the `engineering_journal_entries` unique constraint on `(tenantId, applicantId, missionId, entryDate)` so testing mode can allow duplicate dates.
- **DB functions** (`packages/db/src/feature-flags.ts`): `isFeatureFlagEnabled`, `listFeatureFlags`, `setFeatureFlag`, `deleteFeatureFlag`, `KNOWN_FEATURE_FLAGS`, `JOURNAL_TESTING_MODE_FLAG`.
- **Journal gating** (`packages/db/src/journal.ts`): `createJournalEntry` and `updateJournalEntry` read the flag; when enabled, skip date-conflict, future-date, before-mission-start, and locked checks. `normalizeJournalEntryDate` accepts `allowFuture` param.
- **Readiness gating** (`packages/db/src/submission-readiness.ts`): `getMissionSubmissionReadiness` reads the flag; when enabled, `requiredJournalCount` = 0 (no 4-entry gate). `getMissionSubmissionReadinessWithClient` accepts `requiredJournalCount` param. `submitSubmission` passes the count to the in-transaction re-check.
- **Ops console** (`apps/ops/src/server.ts`, `apps/ops/src/ui.ts`): `GET/POST/DELETE /api/ops/flags` endpoints + "Feature Flags" panel with toggle switches in the UI.

## Out of Scope

- Tenant-scoped flags (currently global only — a `tenantId` column can be added later).
- pgvector/embeddings for semantic flag retrieval (not needed).
- Server-side persistence of flag change audit logs (the `FeatureFlag.updatedAt` tracks the last change).

## Test Scenarios

### Scenario S1: Journal testing mode off — normal restrictions enforced
- **Actor**: Accepted applicant with Mission 1 assigned.
- **Preconditions**: `journal.testing_mode` flag is off (or no flag row exists).
- **Steps**: Try to create a second journal entry for the same mission on the same date.
- **Expected result**: Rejected with "You already have a journal entry for this mission on this date."
- **Automation**: Added this iteration — `journal.test.ts` existing tests pass with `featureFlagFindUnique` mocked to `{ enabled: false }`.

### Scenario S2: Journal testing mode on — duplicate date allowed
- **Actor**: Accepted applicant with Mission 1 assigned.
- **Preconditions**: `journal.testing_mode` flag is enabled.
- **Steps**: Create two journal entries for the same mission on the same date.
- **Expected result**: Both entries are created successfully (no date-conflict error).
- **Automation**: Deferred — requires a real DB with the flag set; verified by manual testing.

### Scenario S3: Journal testing mode on — future date allowed

- **Steps**: Create a journal entry with a future date.
- **Expected result**: Entry is created successfully (no "future date" error).
- **Automation**: Deferred — requires a real DB with the flag set.

### Scenario S4: Journal testing mode on — locked entry editable
- **Actor**: Accepted applicant with a submitted mission (entries locked).
- **Preconditions**: `journal.testing_mode` flag is enabled.
- **Steps**: Edit a locked journal entry.
- **Expected result**: Entry is updated successfully (no "locked" error).

- **Actor**: Accepted applicant with 0 journal entries.

- **Actor**: Ops console user (SUPER_ADMIN or ORG_ADMIN).
- **Preconditions**: Ops console running, applicant portal running.

## Security and Data Rules

- The flags API (`/api/ops/flags`) requires a Keycloak session (SUPER_ADMIN or ORG_ADMIN) — same auth as all ops endpoints.
- `isFeatureFlagEnabled` reads from the DB on every call — no caching, so a flag change is immediately visible to all services.
- The `FeatureFlag` table is global (not tenant-scoped) — flags apply across all tenants. This is acceptable for a local-testing tool; tenant scoping can be added later.
- Dropping the `engineering_journal_entries` unique constraint means production integrity for one-per-mission-per-date is now enforced by the application-layer `assertEntryDateAvailable` check only. In normal mode (flag off), this check is active. In testing mode (flag on), duplicates are allowed by design.
